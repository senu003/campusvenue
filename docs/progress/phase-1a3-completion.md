## 1. Executive Summary & Scope

Phase 1A.3 completes the Phase 1A Authentication suite by introducing an end-to-end, production-grade password recovery and reset capability. Users who forget their credentials can request a password recovery email, receive a cryptographically signed expiring reset link via the local Development Mailbox, enter and confirm a new password satisfying university complexity rules, and immediately log in with their updated credentials.

All operations maintain strict defense-in-depth principles: zero client trust, server-side anti-enumeration defenses via generic reset responses, rate limiting, anti-CSRF token protection, single-use token invalidation, URL fragment token isolation, and pre-reset session cookie revocation via ASP.NET Core Identity's security stamp validator.

## 4. Key Security Invariants & Behavioral Guarantees

### 1. Generic Reset Responses (Anti-Enumeration)
- When `POST /api/auth/forgot-password` receives a validly formatted email address, it returns the exact same HTTP 200 OK generic response regardless of whether the account exists, is unconfirmed, or is confirmed:
  ```json
  {
    "message": "If this email address is registered and eligible, a password reset link has been sent. Please check your inbox."
  }
  ```
- This behavior is formally verified in automated integration tests for unknown accounts, unconfirmed accounts, and confirmed accounts alike.

### 2. URL Fragment Token Isolation (Keeping Tokens Out of Initial HTTP Requests)
- Transactional password reset links sent to users are formatted with a URL fragment:
  ```
  http://localhost:3000/?tab=reset-password#userId={user.Id}&token={Uri.EscapeDataString(token)}
  ```
- **Security Invariant**: According to RFC 3986, web browsers **never** transmit the fragment component (`#...`) in the HTTP request line sent to the host server or intermediate reverse proxies. The browser's HTTP GET request is strictly `GET /?tab=reset-password HTTP/1.1`.
- The React Single Page Application reads `userId` and `token` client-side from `window.location.hash`, initializes the `ResetPasswordForm`, and immediately clears both the fragment and query parameters from browser history via `window.history.replaceState`. This prevents tokens from being written to server access logs or leaking through browser history.

### 3. Dedicated Token Provider & Independent Lifespans
- **Dedicated Provider Scope**: Password reset tokens are generated by `PasswordResetTokenProvider<ApplicationUser>` registered under `PasswordResetTokenProviderDefaults.ProviderName`. Its lifespan is scoped to **2 hours** (`PasswordResetTokenProviderOptions.TokenLifespan = TimeSpan.FromHours(2)`).
- **Email Confirmation Preservation**: Email confirmation continues to use ASP.NET Core Identity's default data protection provider (`TokenOptions.DefaultProvider`), preserving its standard **24-hour** default lifetime (`DataProtectionTokenProviderOptions.TokenLifespan = TimeSpan.FromDays(1)`).
- **Regression Assertion**: An explicit regression assertion test (`TokenProviders_HaveIndependentlyConfiguredLifespans`) validates that configuring the password reset provider's 2-hour lifespan leaves the email-confirmation provider's 24-hour lifespan untouched and completely independent.
- Reset links and tokens are never returned in JSON response bodies or written to server logs.

### 4. Single-Use Tokens & Token Reuse Prevention
- Calling `UserManager.ResetPasswordAsync(user, token, newPassword)` inherently updates `user.SecurityStamp`.
- Because Identity's `DataProtectorTokenProvider` embeds and validates the user's security stamp, mutating the security stamp instantly and permanently invalidates the used token. Any subsequent attempt to use the same token fails with HTTP 400 Problem Details (`"title": "Password Reset Failed"`).

### 5. Session Invalidation & Security Stamp Delay
- When a user logs in, their session cookie contains a snapshot of `user.SecurityStamp`.
- Upon password reset, `user.SecurityStamp` changes in the database.
- ASP.NET Core Identity's `SecurityStampValidator` periodically re-validates active cookie claims against the database.
- **Configured Delay**: In `Program.cs`, `SecurityStampValidatorOptions.ValidationInterval` is explicitly configured to **5 minutes** (`TimeSpan.FromMinutes(5)`).
- After the configured validation interval has elapsed, any session cookie created prior to the password reset is rejected by `SecurityStampValidator`, forcing re-authentication with the new password.

## 5. Email Verification Mechanics: Local Mailbox vs. Production Delivery

### Local Development Mailbox Verification
- In Development mode, `DevMailboxService` operates as an in-memory transactional email sink.
- All outgoing verification and password reset emails are intercepted in memory without generating external network traffic or requiring third-party credentials.
- The captured messages are inspected via:
  1. The standalone HTML inbox at `/dev/mailbox` (available only when `ASPNETCORE_ENVIRONMENT=Development`).
  2. The JSON API at `GET /api/dev/mailbox` consumed by the embedded **Dev Mailbox** navigation tab in the React SPA.
  3. Direct in-memory inspection in automated integration tests via `DevMailboxService.GetMessages()`.

### Production Email Delivery
- In Production mode, transactional emails are dispatched via the `IEmailSender` interface backed by a configured institutional SMTP relay or cloud mail provider (e.g. Amazon SES, SendGrid, or university mail exchange).
- Development mailbox routes (`/dev/mailbox` and `/api/dev/mailbox`) are strictly disabled in Production (`app.Environment.IsDevelopment()` gate).
- Production email verification requires live SMTP credentials configured through production environment variables, preserving zero-secret hygiene in development.
